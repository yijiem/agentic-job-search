# Performance and concurrent editing

Saving a role, editing a resume review, or creating an application batch should not wait for the job-search workflow to finish. The implementation separates these user commands from the long workflow lock, acknowledges their committed records directly, and refreshes preparation and reports afterward. This document describes the implemented boundaries, measurements from the November 15, 2026 investigation, and remaining work. It does not establish that a particular deployment has been upgraded.

**User commands and consistency.** `python3 -m jobflow action --request FILE` handles application, task and interview updates, batch creation/material edits, resume uploads/defaults/contact details/text drafts/version saves, PDF review changes and local PDF suggestions. The allowlist lives in `jobflow/foreground.py`. These commands do not acquire `workflow.lock` or borrow the background worker's renewable workspace lease.

The command reads its required records, validates the requested changes, and buffers its writes. A short compare-and-set transaction checks that the shared records and collections it read still match before committing the entire command. Collection checks protect decisions such as avoiding duplicate active batches. Unrelated source freshness updates do not invalidate a user save. Hosted reads are cached within the command, and helper reads of resume settings see the command's own buffered changes. The response is returned only after commit.

This is optimistic concurrency, not removal of synchronization. SQLite still serializes its short write transactions; the hosted transaction briefly locks the workspace row to validate and commit. Conflicting shared-record edits are rejected atomically. The CLI rereads and retries a known no-write conflict at most three times. Network failures, timeouts and uncertain responses are not automatically replayed as creations: the server might already have committed them. A stale PDF review or reserved application batch still requires review of the current version. Authentication, account routing, CSRF validation and submission authorization remain required.

Background writes to shared preparation/application records also check their observed inputs, so an older plan cannot overwrite a newly completed task or user note. The hosted migration additionally fences older worker versions from writing protected records after an intervening foreground commit. Job ingestion continues to own job/source-health updates. This does not yet make arbitrary manual job ingestion a concurrent foreground operation; saving an existing role to the application tracker is the supported fast path.

**Durable files and deferred work.** A new resume version uploads immutable bytes before publishing its manifest and associated records together. Foreground publication is restricted to new application-resume paths and the workspace's content-hashed objects. Original versions remain intact. Failed publication must not be presented as a saved version; remote unreferenced objects remain eligible for the existing garbage-collection process.

Application, task and interview changes request a preparation/report refresh separately from their primary write. Supabase commits the queue request in the same database transaction as the edit. The disk-backed cloud server also queues a refresh. A later projection failure does not undo the saved application or task.

For `python3 -m jobflow web`, `jobflow/local_refresh.py` reads only `projection_requests/current` every two seconds and launches the existing `refresh` CLI in a separate process. It retries a busy workflow lock or failed refresh, coalesces completed requests, and notices a newer request that arrived during computation. A retained request is processed on server startup. Shutdown cancels the refresh subprocess with bounded waits. Preparation/report freshness therefore remains eventual; it is separate from the immediate save acknowledgement. Local CLI actions made while the web server is closed retain their marker for the next start, or can be followed by an explicit `python3 -m jobflow refresh`.

The browser tracks pending mutations by affected records instead of disabling unrelated actions globally. It merges returned application/task/interview records without waiting for a full workspace reload, retains unsaved editor state, and defers broad rendering while an editor is active. Opening Resumes and Application batches now reads their libraries; it does not synchronize earlier uploads as a hidden write. **Restore earlier uploads** explicitly invokes the existing resume synchronization operation. PDF annotation recovery from tab-scoped storage retains its existing synchronization behavior.

**Search computation.** `jobflow/workflow.py` reads the saved jobs once, builds canonical-URL and source-ownership indexes, and processes only the owning source's jobs when evaluating omissions. It retains the existing three concurrent feed fetches. Successfully fetched jobs update freshness and lifecycle fields, while job writes are grouped into batches of at most 50 rows.

Matching results carry a signature of the ranking inputs, profile, search preferences and `MATCHING_VERSION`. Unchanged inputs reuse persisted results; new or changed jobs are scored once instead of being scored again in a final full-corpus pass. Legacy jobs receive a signature when next evaluated. Preference/profile changes invalidate the signature, including for stored jobs not returned by a feed; a scoped retry still leaves unrelated sources untouched. Bump `MATCHING_VERSION` whenever ranking behavior or its input dependencies change. The existing explicit `rematch` command remains available.

Successful complete feed snapshots remain the only basis for omission tracking. One omission marks a job missing; two mark it closed. A failed source does not advance either counter. Reappearing jobs reopen, authoritative source ownership is preserved, and imports cannot provide an arbitrary cached score. Search does not edit completed tasks, application history or resume evidence.

**Initial loading.** `/api/state` still returns a workspace snapshot, but packet entries now contain only IDs and job IDs. Full packet text remains available in role details. The current plan includes its notes and research notes without duplicating the task list and Markdown export; unused `plans` and `coaching` arrays retain empty-array contract shapes. Existing startup optimizations also include an early state request, deferred map assets, description-free job projections, compressed responses and request-scoped file metadata reuse. See [the web app guide](WEB_APP.md) for the existing startup request-count fixtures.

Measurements used the local snapshot of 26,907 jobs, with 165 configured live feeds and 143 manual sources. These are read-only developer-machine measurements and deterministic test observations, not live hosted latency results or promises.

| Measurement | Observation | Interpretation |
| --- | --- | --- |
| Full job-body SQL read plus JSON decoding before the change | 0.852 seconds for approximately 200.4 million JSON characters | Repeating this once per successful source was avoidable work. |
| One pure matching pass before the change | 42.161 seconds over 26,907 jobs | Avoiding unchanged matching removes substantial CPU work; this excludes feeds and writes. |
| Search regression tests after the change | One corpus read; one match per new/changed role; zero matching calls for identical subsequent inputs | Guards the work performed without relying on timing-sensitive assertions. |
| Serialized initial snapshot | 14,073,686 → 10,158,357 bytes, a 27.8% reduction | Packet and duplicate plan/coaching projection changes only. |
| The same snapshots compressed with Python `gzip.compress` defaults | 1,136,898 → 853,800 bytes, a 24.9% reduction | Comparable compression experiment; actual HTTP bytes depend on server compression settings. |
| Full report dry run, with writes mocked out | 398 files, 237.11 MiB serialized, 3.053 seconds compute/serialization | Excludes filesystem writes, compression and remote calls; the jobs export alone was 229.71 MiB. |
| Rewriting the original job corpus using existing remote batch limits | 799 write batches | Shows why avoiding unnecessary rewrites matters more than merely increasing batch size. |

The original per-source scans would imply roughly 140 seconds of decoding at this snapshot size if all 165 live feeds succeeded and each scan cost the measured 0.852 seconds. That is an extrapolation, not an end-to-end benchmark. No live feeds or real user mutations were used for these measurements.

**Remaining limits.** `/api/state` is still large and monolithic, and non-job records are still read before projection. Jobs repeat office/salary evidence, research is sent broadly, some role-detail reads include unrelated record families, and list filtering is largely in the browser. Full report regeneration remains expensive. Freshness updates still write fetched job bodies even when their descriptions are unchanged. These improvements reduce unnecessary work; they do not establish production latency targets.

The checked-in Blueprint uses free web compute and a cron worker at minutes 7, 22, 37 and 52. A newly queued projection may wait nearly 15 minutes for the next scheduled check, plus earlier queued/running work. Render delays a scheduled cron start while the previous run remains active. Free web instances also spin down after inactivity and require a cold start; that delay is separate from Python/API/browser work. Current provider behavior is described in [Render's free web service documentation](https://render.com/docs/free) and [cron documentation](https://render.com/docs/cronjobs). Always-on compute or a continuously running queue worker is an explicit hosting/cost choice, not part of these changes.

Operations outside the foreground allowlist keep their existing lock/lease and review boundaries: examples include Codex run preparation/submission operations, paid AI suggestions, earlier-upload restoration, background/profile preference changes, and agentic planning. A prolonged search may still delay those operations. Uploads and reads still depend on the network. Success cannot be guaranteed during a network outage, service failure, invalid input or conflicting edit; the requirement is to avoid unrelated workflow contention and preserve truthful save status.

**Next implementation priorities.**

1. Add small paginated endpoints for company counts, role lists, applications and role details. Fetch only the active view, index its filter/order columns, and load resume/research/packet bodies on demand. Keep evidence catalogs separate and reference them by ID instead of repeating them in every job. Preserve access checks and private cache boundaries.
2. Introduce durable operation IDs and stored outcomes for creations and uploads. This permits safe reconciliation after a lost response and, eventually, safe retry of an uncertain request. A retry header alone does not provide this guarantee. Keep submission safeguards separate from ordinary editor saves.
3. Publish derived views and exports by input revision. Rebuild affected companies/packets only, coalesce pending refreshes, and generate the complete historical job export on demand or on a separate schedule. Store source observations separately from large immutable description bodies.
4. If prompt background completion is required, run a continuous durable queue worker with separate priorities for short projection jobs and long feed searches. Add per-source checkpoints, bounded in-flight fetches, total time budgets, cancellation and rate-limit-aware retries. Measure before increasing feed concurrency beyond three.
5. Instrument request latency, queue delay, database/RPC counts and bytes, transaction duration, conflicts/retries, feed timings, rows changed and projection duration. Measure browser first useful render and input responsiveness with warm and cold caches. Compare p50/p95 saves during a search with idle saves, and separate network/cold-start delay from application processing. Avoid logging resume text, credentials or private payloads.

Verification uses temporary workspaces, fake remote services and mocked feeds.
